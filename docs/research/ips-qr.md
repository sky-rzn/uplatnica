# NBS IPS QR ("IPS Skeniraj"): спецификация для генератора

Исследование выполнено 2026-11-13. Пометки в тексте:

- **[норма]** — нормативный текст НБС (Прилог 1 к Одлуке).
- **[рекомендация НБС]** — официальные, но ненормативные рекомендации НБС.
- **[валидатор]** — фактическое поведение официального валидатора НБС
  (`https://nbs.rs/QRcode/api/qr/v1/validate`), проверенное запросами
  2026-11-13. Нормой это не является, и НБС может поменять валидатор
  без предупреждения.
- **[вторично]** — сторонние open-source реализации.
- **НЕ ПРОВЕРЕНО** — подтвердить по первоисточнику не удалось.

## 0. Источники и версия спецификации

Действующая норма — **Прилог 1** («Стандардизована дводимензионална
ознака (QR – Quick Response)») к *Одлуке о општим правилима за
извршавање инстант трансфера одобрења*, «Службени гласник РС»,

Важно про английский перевод S1: в нем у тега I десятичным
разделителем указана точка («RSD1025.1», «RSD0.01»), а разделителем
тысяч — запятая. **Это артефакт перевода.** В сербском оригинале (S4)
написано «децимални зарез», примеры «RSD1025,» / «RSD1025,1», а
«RSD1025.00» валидатор отвергает (см. §6.3). Канонический формат —
**с запятой**.

## 1. Типы кода (тег K)

[норма, S1/S4]:

| K | Назначение |
|---|---|
| `PR` | IPS QR код получателя платежа, в т.ч. на счете-фактуре. **Этот тип нужен нам** (уплатница / счет) |
| `PT` | Код на кассе торговца, показывает торговец |
| `PK` | Код на кассе торговца, показывает плательщик (покупатель) |
| `EK` | Код в ПО интернет-магазина (e-commerce) |

Код с `K:PR` положено помечать надписью **«NBS IPS QR»** непосредственно
над, рядом или под кодом [норма, S1/S4]. В S8 это сказано как
обязательное: «it is obligatory to state the NBS IPS QR next to, below or
above the NBS IPS QR code». Генератор НБС подписывает «NBS IPS QR» под
изображением [валидатор: так выглядит PNG от `/generate`].

Для PT/EK торговцу нужен договор с банком-эквайером. Генерировать их
самостоятельно не предполагается [S8, «Important notes»]. Тип PK
валидатор НБС не поддерживает: ответ `622 Entered IPS QR code ID is not
supported.` [валидатор].

## 2. Таблица тегов (действующая редакция 125/2020)

Таблица воспроизводит S1 и S4. Обозначения: M — обязательный,
O — опциональный, M(p) — обязательный, но плательщик может его изменить,
O(n) — опциональный, неизменяемый, «-» — не используется.
«Неизм.» — после сканирования банк не вправе менять поле.

| Тип | Макс. | Тег | Описание | PR | PT | PK | EK | Неизм. |
|---|---|---|---|---|---|---|---|---|
| 3a | 3 | K | Identification code | PR | PT | PK | EK | √ |
| 2n | 2 | V | Version: 01 | 01 | 01 | 01 | 01 | √ |
| 1n | 1 | C | Code set: 1 = UTF-8 | 1 | 1 | 1 | 1 | √ |
| 18n | 18 | R | Счет получателя | M | M | - | M | √ |
| 1..70ans | 70 | N | Получатель (Payee's name) | M | M | - | M | √ |
| 5..18an | 18 | I | Валюта и сумма | **M(p)** | M | O | M | √ |
| 18n | 18 | O | Счет плательщика | - | - | M | - | √ |
| 1..70ans | 70 | P | Данные о плательщике | O | - | O | - | |
| 3n | 3 | SF | Шифра плаћања | M | M | - | M | |
| 1..35ans | 35 | S | Сврха плаћања | O | O | O(n) | O | |
| 4n | 4 | M | MCC (ISO 18245) | - | M | - | M | √ |
| 5..10an | 10 | JS | Одноразовый код плательщика (TOTP) | - | - | O | - | √ |
| 5..8an | 8 | RK | Референца плательщика | - | - | O | - | √ |
| 1..25an | 25 | RO | Модель + позив на број одобрења | O | M | - | M | √ |
| 1..140an | 140 | RL | Референца получателя (свободная форма) | O | - | - | - | |
| 19an | 19 | RP | Референс транзакции на кассе | - | M | - | M | √ |

**RO, RL и RP взаимоисключающие** («Узајамно искључиви» /
«Mutually exclusive»). В таблице S1/S4 пометка стоит на группе
RO/RL/RP [норма]. Валидатор на `RO` + `RL` в одном коде отвечает
`613 Fields are mutually exclusive. ['Multiple mutually exclusive tags are specified: [RO, RL]']`
[валидатор].

Типы символов [норма, S4: «Појашњење ознака у колони „Тип карактера”»]:

- `a` — прописные и строчные буквы **латиницы** сербского и английского
  языков;
- `n` — цифры 0–9;
- `s` — спецсимволы из таблицы в конце Прилога (см. §3.3);
- `an` — буквы + цифры; `ans` — буквы + цифры + спецсимволы.

### 2.1. Набор тегов для K:PR

Для `K:PR` допустимы только `K, V, C, R, N, I, P, SF, S, RO, RL`
[норма + валидатор]. На любой другой тег (`O`, `M`, `JS`, `RP`, `X`, …)
валидатор отвечает
`601 Not an IPS QR code. ['Tags allowed [K, V, C, R, N, I, P, SF, S, RO, RL] not allowed: …']`.

| Тег | PR | Итоговое правило для генератора |
|---|---|---|
| K | M | ровно `PR`, заглавными (`K:pr` дает 601) |
| V | M | ровно `01` (`V:1` дает 608) |
| C | M | ровно `1` |
| R | M | 18 цифр, контрольные цифры по mod 97 (см. §2.2) |
| N | M | 1..70 символов, до 3 строк, латиница + спецсимволы |
| I | M(p) | `RSD` + сумма через запятую (см. §2.3) |
| P | O | 1..70 символов, до 3 строк |
| SF | M | 3 цифры, первая 1 или 2, код из Прилога 3 (см. §2.4) |
| S | O | 1..35 символов, одна строка |
| RO | O | модель (2 цифры) + позив на број, всего ≤ 25 (см. §2.5) |
| RL | O | ≤ 140, только буквы и цифры. Взаимоисключающий с RO |

### 2.2. R — счет получателя

- Ровно 18 цифр, «без размака и цртица» [норма, S1/S4].
- Короткий формат `банк-номер-контроль` дополняется нулями **в середине**
  (после 3-значного кода банка). Примеры [рекомендация НБС, S6]:
  - `840-955845-10` → `|R:840000000095584510|`
  - `165-55-74` → `|R:165000000000005574|`
  - `310-1234567891211-86` → `|R:310123456789121186|`
- Последние 2 цифры — контрольный номер по ISO 7064 mod 97-10:
  `98 - (первые_16_цифр * 100) mod 97`. Сама Прилог 1 этого не
  требует. Но **валидатор проверяет**: на `845000000040484988` отвечает
  `608 … Tag R - number of payee's account is not determined according to model 97`
  [валидатор]. Алгоритм совпадает с примерами НБС: для `8400000000955845`
  выходит `10`, для `1650000000000055` выходит `74`.
- В коде только один счет получателя [рекомендация НБС, S6].

### 2.3. I — валюта и сумма

[норма, S4; сербский оригинал]:

- Формат `RSD` + сумма. Десятичная **запятая обязательна**. Незначащие
  нули после нее можно не писать: `RSD1025,` и `RSD1025,1` корректны.
- Минимум `RSD0,01`, максимум `RSD999999999999,99` (12 цифр целой
  части).
- Разделители тысяч (`.`) не используются.
- Целую часть опускать нельзя: `RSD,01` неверно, `RSD0,01` верно.
- В NBS IPS QR (PR) получатель может указать нулевую сумму:
  `RSD0,00` или `RSD0,`.
- Длина значения 5..18 символов.
- Между `RSD` и суммой нет пробела [рекомендация НБС, S6].
- Для PR сумма M(p): плательщик может изменить ее в банковском
  приложении [норма].

Проверено валидатором:

| Значение | Результат |
|---|---|
| `RSD3702,65`, `RSD1025,`, `RSD1025,1`, `RSD0,`, `RSD0,00`, `RSD0,01`, `RSD999999999999,99` | 0 OK |
| `RSD0001,00` (ведущие нули) | 0 OK (принимается; норма об этом молчит) |
| `RSD1025` (нет запятой) | 608 |
| `RSD,01`, `RSD,` | 608 |
| `RSD1.025,00` (разделитель тысяч) | 608 |
| `RSD1025.00` (десятичная точка) | 608 |
| `RSD1025,123` (3 знака после запятой) | 608 |
| `RSD 1025,00` (пробел) | 608 |
| `EUR10,00`, `rsd10,00` | 608 |
| `RSD-5,00` | 608 |
| `RSD1000000000000,00` (13 цифр) | 608 + «Tag I must contain between 5 and 18 alphanumeric characters» |

Регулярное выражение, согласованное с нормой и валидатором (выведено
нами, а не взято из источника):
`^RSD(0|[1-9][0-9]{0,11}),[0-9]{0,2}$`. Валидатор принимает и ведущие
нули, то есть фактически `^RSD[0-9]{1,12},[0-9]{0,2}$`. Генератору лучше
выдавать канонический вид с двумя знаками после запятой, например
`RSD3596,13`.

### 2.4. SF — шифра плаћања

- 3 цифры. Первая — форма платежа, две следующие — основание [норма].
- Коды задает Прилог 3 Одлуки о платним налозима (S12): формы
  `1` (gotovinski), `2` (bezgotovinski), `3` (obračunski),
  `9` (preknjižavanje). Основания: 20–31, 40–42, 44–49, 53, 54, 57, 58,
  60–66, 70–73, 75–90. Код 29 «Digitalna imovina» есть в текущем
  консолидированном тексте S12 (последнее изменение 82/2024).
- Для PR валидатор требует первую цифру 1 или 2 и основание из
  Прилога 3: «Payment code is incorrect. Must be three digits allowed by
  regulation. For invoices, the first digit must be 1 or 2.»
  [валидатор]. Принимаются 120, 121, 129, 131, 153, 165, 189, 190, 229,
  254, 288, 289, 290. Отвергаются 89, 101, 143, 150, 191, 199, 200, 243,
  389, 999. Это согласуется с Прилогом 3 (оснований 43, 50, 91, 99, 00
  нет).
- 189/289 («Transakcije po nalogu građana») по рекомендации S6 только для
  платежей домохозяйств. Юрлица и предприниматели используют другие
  коды. Частые коды для счетов: 121/221, 122/222 [рекомендация НБС, S6].
- Полный перечень кодов — в `docs/research/payment-codes.md` /
  `payment-codes.json` (отдельный документ).

### 2.5. RO — модель и позив на број одобрења

[норма, S1/S4]:

- Первые 2 цифры — номер модели (например 97, 11). Если позив на број не
  построен ни по одной модели, первые две цифры `00`.
- Содержимое пишется подряд, без пробелов (`0074879`).
- Дефис допускается только для разделения групп символов
  (`0014-1234-12`). **Исключение: модель 97, там дефисы запрещены**
  (`9714123412`).
- Максимум **25** символов (тип `1..25an`). В старой редакции 2018 года
  (S5) было `0..35n/an`, 35 символов. Это устарело.

[рекомендация НБС, S6]:

- Одна строка, без переводов строки. Если RO последний тег, после него
  ничего нет.
- Примеры (все корректны):
  - `|RO:001234` — номер 1234 без модели;
  - `|RO:9714123412` — модель 97, контрольный номер 14, номер 123412;
  - `|RO:009714123` — номер 9714123 без модели;
  - `|RO:00009714-1342` — номер `009714-1342` без модели.
- Если номер без модели, а `00` не поставлено, код технически корректен
  (прочтется как другая модель). Получатель отвечает за это сам: банк
  отвечает за содержимое только при модели 97.

Модель 97 (S12, Прилог 2, т. 9 Одлуки о платним налозима): буквы
переводятся в числа A=10 … Z=35, к числу справа приписывается `00`,
контрольный номер = `98 - (N mod 97)`, две цифры с ведущим нулем.
Длина позива на број по модели 97 — до 23 знаков, включая 2 контрольные
цифры. Вместе с моделью `97` выходит 25, что совпадает с лимитом RO.
Пример из нормы: `567812F48K012` → `567812154820012` →
контрольный номер 54 → `54567812F48K012`. Банк обязан **отклонить**
платеж, если контрольный номер не соответствует модели 97: «Pružalac
platnih usluga neće izvršiti platne naloge kod kojih se kontrolom utvrdi
da kontrolni broj … ne odgovara naznačenom broju osnovnog modela»
[норма, S12]. Проверяет ли это конкретный банк при оплате по QR,
**НЕ ПРОВЕРЕНО**. Валидатор НБС это проверяет.

Проверено валидатором:

| RO | Результат |
|---|---|
| `001234`, `1234`, `1112345`, `2212345`, `00ABC123`, `00abc123`, `0014-1234-12`, `9714123412`, `9754567812F48K012`, `97163220000111111111000`, `00` + 23 цифры (25 символов) | 0 OK |
| `9715123412` (неверный контрольный номер) | 608 «…not determined according to model 97» |
| `9714-123412` (дефис в модели 97) | 608 |
| `00 1234` (пробел), `00123/24` (слэш) | 608 «…for other models … numbers, letters and dashes are correct» |
| `00` (только модель) | 608 «Tag RO must consist of a model (2 digits) and a payee's reference credit number» |
| 26 символов | 608 «…must not exceed 25» |

Итого для RO (вывод из нормы и валидатора): `^[0-9]{2}[A-Za-z0-9-]{1,23}$`.
При модели 97 дефисы запрещены и проверяется mod 97. Остальные модели
(11, 22 и т. д.) валидатор по содержимому не проверяет: проходят и
`1112345`, и `1112346`, а по одному алгоритму оба верными быть не
могут. Буквы в модели 97 принимаются только заглавные:
`9754567812f48k012` дает 608.

### 2.6. N и P — получатель и плательщик

[норма, S1/S4]:

- N обязателен: имя и фамилия или наименование получателя. Можно
  добавить адрес (улица и номер, место).
- Данные в 1, 2 или 3 строках, разделенных символом новой строки.
  Пробелы входят в лимит 70.
- P опционален: имя и фамилия или наименование, адрес. 1–3 строки,
  ≤ 70 символов.
- «Код тагова N и P … треба имати у виду различите оперативне системе и
  начине одвајања нове линије» [норма, S4]. В примерах S8 перевод строки
  записан как `\r\n`.

[рекомендация НБС, S6]: P лучше не указывать, если получатель учитывает
оплату по позиву на број. Банк может заменить P на реального владельца
счета. Пустой `|P:|` недопустим.

Проверено валидатором:

- `\n`, `\r\n` и даже одиночный `\r` принимаются как разделители строк.
  4 строки дают 608 «must not contain more than 3 lines».
- Лимит 70 считается **в символах (code points), а не в байтах**:
  70 × `Č` проходит. Перевод строки входит в лимит: `\n` считается за 1
  символ, `\r\n` — за 2 (35+`\r\n`+33 проходит, 35+`\r\n`+34 дает
  608).
- Пробелы в начале и в конце значения, двойные пробелы, табуляция и
  пустая строка внутри N принимаются. Принимать это все же не
  рекомендуется: рекомендация S6 п.3 запрещает лишние пробелы и
  переводы строк вне содержимого.
- **Кириллица отвергается**: `N:ЈП ЕПС БЕОГРАД` дает 608 «Tag N can
  contain numbers, letters and special characters in accordance with
  regulation». То же для S. Это согласуется с определением типа `a`
  (только латиница), хотя кодировка UTF-8. **Генератор обязан
  транслитерировать кириллицу в латиницу** (Ђ→Đ, Љ→Lj, Њ→Nj, Џ→Dž,
  Ћ→Ć, Ч→Č, Ш→Š, Ж→Ž и т. д.).
- Сербские диакритики `Č Ć Ž Š Đ` и строчные `č ć ž š đ` проходят.
- `Ä`, `§`, `€`, `\`, NBSP (U+00A0), emoji, `¦` дают 608.

### 2.7. S — сврха плаћања

1..35 символов `ans`, **одна строка**, перевод строки запрещен
[норма + S6]. Проверено валидатором: 35 проходит, 36 дает 608, `A\nB` дает
608 «must not contain more than one line», кириллица дает 608.

### 2.8. RL — референца примаоца плаћања

Норма: свободная форма, `1..140an`. Валидатор пропускает **только буквы
и цифры**: пробел и дефис дают 608 «In tag RL, only alphanumeric
characters are allowed». С RO не сочетается. Банковская поддержка RL на
практике **НЕ ПРОВЕРЕНО**. Для уплатницы RL не нужен, используем RO.

## 3. Формат записи

### 3.1. Разделители

[норма, S1/S4, «Формат записа» / «Entry format»]:

- Каждое поле — пара `ТЕГ:значение`. Поля разделяются `|` («pipe»).
- «Последње поље у садржају завршава се крајем записа» — после
  последнего поля ничего нет.
- «**Делимитер не сме бити део садржаја поља**». Экранирования нет.
- Теги опциональных полей не пишутся, если у них нет значения.

[рекомендация НБС, S6, пп. 1–6]:

- Тег отделяется от значения двоеточием `:`.
- Запись начинается сразу, без пустых символов и строк в начале.
- Теги пишутся подряд, без пробелов и переводов строк между полями.
- Запись не может начинаться с `|`.
- После последнего символа нельзя ставить `|`, пробел или перевод строки.
- `|S:|` (пустой тег) недопустим.

Проверено валидатором:

| Вход | Код ответа |
|---|---|
| завершающий `\|` | `620 String cannot end with \| character.` |
| ведущий `\|` | `619 String cannot start with \| character.` |
| завершающий/ведущий пробел, `\n`, `\r\n` | `602 … Text cannot start or end with whitespaces.` |
| пробел после `\|` (`\| V:01`) | `602 … Tags must be listed immediately after the delimiter` |
| `\|S:` (пустое значение) | `602 … The specified tag must have a value.` |
| повторный тег | `605 … Tag S appears multiple times.` |
| `S` без `:` | `602 … Name and value of tag must be separated with :` |
| `A\|B` или `A\\\|B` внутри N | разбивается по `\|`, `602` — экранирования нет |
| `:` внутри значения (`S:a:b`) | 0 OK (делится по первому `:`) |
| UTF-8 BOM в начале | `601 … not allowed: ﻿K` — **BOM запрещен** |

Вывод для генератора: символ `|` из пользовательского ввода нужно
удалять или запрещать. Это также следует из того, что `|` нет в таблице
разрешенных спецсимволов.

### 3.2. Порядок тегов

Норма порядок явно не устанавливает. Пример в норме и в S8 идет в
порядке таблицы: `K, V, C, R, N, I, (P), SF, (S), (RO)`. Валидатор
принимает **любой порядок**: `V` перед `K`, `N` перед `R`, `SF` перед `I`,
`RO` перед `S` — все 0 OK. В невалидном примере S8 теги тоже
перемешаны, а ошибка только «String cannot end with |».

Рекомендация: всегда выдавать порядок таблицы
`K|V|C|R|N|I|P|SF|S|RO`. Так делает сама НБС, и это безопаснее для
банковских сканеров, которые могли реализовать разбор упрощенно.
Обязательность порядка в банковских приложениях **НЕ ПРОВЕРЕНО**.

### 3.3. Кодировка и набор символов

- `C:1` означает UTF-8, обязательно [норма + S6 п.9].
- Буквы — только латиница сербского и английского алфавита
  (`A–Z a–z Č Ć Ž Š Đ č ć ž š đ`) [норма, тип `a`; валидатор].
- Спецсимволы [норма; таблица из S4, стр. 8, сверена по изображению]:

  ```
  !  (  /  @  }
  “  )  :  [  ~
  #  *  ;  ]  „
  $  +  <  ^  ”
  %  ,  =  _  "
  &  -  >  `  ’
  ‘  .  ?  {  '
  ```

  В английском переводе S1 в таблице потеряны `[` и `]`. В S6 и в
  оригинале S4 они есть. `|` и `\` в таблице отсутствуют. Строку
  ``!"#$%&'()*+,-./:;<=>?@[]^_`{}~`` валидатор в N принимает, типографские
  кавычки `„ ” ‘ ’ “` тоже.
- Пробел разрешен в `ans` (входит в лимит). Табуляцию валидатор в N
  пропускает, но в таблице ее нет, поэтому не использовать.
- **Кириллица запрещена** (см. §2.6), хотя кодировка UTF-8.

## 4. Требования к QR-изображению

[норма, S1/S4, Прилог 1 т. 1–2]:

- QR по **ISO/IEC 18004**.
- На печатных счетах ширина и высота кода **от 2,5 до 3,3 см**.
- Уровень коррекции для счетов: **M (до 15 %) или L (до 7 %)**. В
  редакции 2018 года (S5) был только M. Для кассы (PT/PK) только L.
- **Максимальная версия — 13** (69×69 модулей). Версия может быть меньше,
  если содержимое позволяет.
- Емкость версии 13 по таблице Прилога (UTF-8, т. е. байтовый режим):

  | Версия | Модули | ECC | Бит | Цифр | Alnum | Байт |
  |---|---|---|---|---|---|---|
  | 13 | 69×69 | L | 3.424 | 1.022 | 619 | **425** |
  | 13 | 69×69 | M | 2.672 | 796 | 483 | **331** |
  | 13 | 69×69 | Q | 1.952 | 580 | 352 | 241 |
  | 13 | 69×69 | H | 1.440 | 427 | 259 | 177 |

  «69x69 модула до 331 бајта, број знакова за UTF-8 може бити мањи ако
  се користе знакови који имају двобајтни кôд» [норма]. **Предел
  полезной нагрузки — 331 байт UTF-8 при M или 425 байт при L.**
- Пример в норме: изображение 25 mm × 25 mm, уровень L [S1/S4].
- Quiet zone и минимальный размер модуля Прилог **не задает**. Действует
  общее требование ISO/IEC 18004: quiet zone не менее 4 модулей. Входит
  ли quiet zone в размер 2,5–3,3 см, **НЕ ПРОВЕРЕНО** (норма не уточняет).
  Расчет (не измерение): при версии 13 и стороне 25 мм без quiet zone
  модуль около 0,36 мм. При типичной версии 7 (45 модулей) около 0,56 мм.
- Генератор НБС (`/generate`, `/gen`) [валидатор, разбор format info
  выданных PNG]: **ECC L**, минимально возможная версия (для эталонной
  строки на 136 символов — версия 7, для строки без S/RO — версия 4),
  поле около 7–8 модулей, подпись «NBS IPS QR» под кодом. PNG 1-бит,
  по умолчанию 150×150 px (S8), `/generate/{size}` задает размер.

### 4.1. Ограничение на суммарную длину (вывод)

Валидатор НБС длину строки в байтах **не проверяет**. Строка на 450
байт UTF-8 (N, P, S целиком из `Č/Ž/Š`) получила 0 OK, хотя в версию 13
она не влезает даже при L. Генератор должен проверять сам. Подсчет по
лимитам полей (арифметика):

- максимум для PR с RO, только ASCII: 4+5+4+21+73+21+73+7+38+29 =
  **275 байт**, укладывается в M;
- если в N, P, S все символы двухбайтные (`Č Ć Ž Š Đ`): +175 = **450
  байт**, превышает 425 (L);
- с RL (140) вместо RO выходит до 390 байт ASCII.

Рекомендуемая стратегия: считать `TextEncoder().encode(s).length`.
До 331 байт — ECC M (предпочтительно для печати). 332–425 — ECC L.
Больше 425 — ошибка, предложить сократить N/P/S.

## 5. API генератора/валидатора НБС (только для разработки)

Документация: S8/S9 (© 2022). Использование бесплатно [S8]. По
условиям S10 введенные данные не хранятся. Отправлять туда реальные
персональные данные пользователей из нашего приложения не следует:
API только для тестов при разработке.

База: `https://nbs.rs/QRcode/api/qr/v1/`. Параметр `?lang=` задает язык
ошибок: `sr_RS_Latn` (по умолчанию), `sr_RS` (кириллица), `en`.

| Метод | URL | Тело запроса | Ответ |
|---|---|---|---|
| gen | `POST /gen`, `POST /gen/{size}` | JSON: объект `{"K":"PR","V":"01",…}` | при успехе `image/png`; при ошибке JSON `{"s":{"code":500,"desc":"Validacija naloga nije prošla."}}` без подробностей |
| generate | `POST /generate`, `POST /generate/{size}` | текст (строка IPS QR) | JSON `{s, t, n, i}`, где `i` — PNG в base64, 150×150 по умолчанию |
| validate | `POST /validate` | текст (строка IPS QR) | JSON `{s, t, n}` или `{s, t, e}` |
| upload | `POST /upload` | `multipart/form-data`, ключ `file`, PNG/JPEG с QR | JSON `{s, t, n}` или `{s, t, e}` |

Поля ответа [S8]: `s` — статус `{code, desc}` (`code: 0` = OK);
`t` — присланный текст; `n` — разобранные теги (JSON); `e` — массив
описаний ошибок; `i` — base64 PNG.

Проверено 2026-11-13:

- `Content-Type: text/plain; charset=utf-8` для `/validate` и
  `/generate` работает. `application/json` для `/gen` работает.
- CORS: `Access-Control-Allow-Origin: *`, методы `GET,HEAD,POST`,
  заголовок `content-type`. Из браузера с localhost вызывать можно.
- В документации S8 пример запроса к `/generate` начинается с `{`
  (`{K:PR|V:01|…`). Это опечатка: с `{` в начале валидатор отвечает
  `601 … not allowed: {K`.
- В S8 сказано, что валидатор проверяет коды «PT and EC». Правильно —
  EK (опечатка в документе).

Пример:

```sh
printf '%s' 'K:PR|V:01|C:1|R:845000000040484987|N:JP EPS BEOGRAD|I:RSD3702,65|SF:289' \
  | curl -sS -X POST -H 'Content-Type: text/plain; charset=utf-8' \
         --data-binary @- 'https://nbs.rs/QRcode/api/qr/v1/validate?lang=en'
```

Ответ:
`{"s":{"code":0,"desc":"Ok."},"t":"K:PR|…","n":{"K":"PR","V":"01",…}}`

Коды `s.code`, встреченные в документации и при проверке:

| code | desc (en) | когда |
|---|---|---|
| 0 | `Ok.` | корректно |
| 500 | `Validation failed.` / `Validacija naloga nije prošla.` | `/gen` с некорректными данными |
| 601 | `Not an IPS QR code.` | неизвестный тег, `K` не того регистра, BOM, нет тега K |
| 602 | `Not in accordance with IPS QR code format.` | пробелы в начале или конце, пустой тег, нет `:`, пробел после `\|` |
| 605 | `Double tag is not in accordance with IPS QR code format.` | повтор тега |
| 608 | `Invalid field format.` | ошибки формата значений (подробности в `e`) |
| 610 | `Mandatory tag missing` | нет K/V/C/R/N/I/SF; для PT — нет M |
| 613 | `Fields are mutually exclusive.` | RO + RL |
| 619 | `String cannot start with \| character.` | ведущий `\|` |
| 620 | `String cannot end with \| character.` | завершающий `\|` |
| 622 | `Entered IPS QR code ID is not supported.` | `K:PK` |

## 6. Тестовые фикстуры

### 6.1. Корректные строки из официальных документов (дословно)

**F1** — пример из действующего Прилога 1 (S1 и S4, стр. 8; текст сверен
по изображению оригинала), уровень L, 25×25 мм:

```
K:PR|V:01|C:1|R:845000000040484987|N:JP EPS BEOGRAD|I:RSD3702,65|SF:289|S:UPLATA PO RAČUNU ZA EL. ENERGIJU|RO:97163220000111111111000
```

Валидатор: 0 OK. RO: модель 97, контрольный номер 16 верен для
`3220000111111111000`.

**F2** — пример из S8 (методы generate/validate/upload). В N и P
многострочные значения, перевод строки `\r\n` (так в поле `t` ответа):

```
K:PR|V:01|C:1|R:845000000040484987|N:JP EPS BEOGRAD\r\nBALKANSKA 13|I:RSD3596,13|P:MRĐO MAČKATOVIĆ\r\nŽUPSKA 13\r\nBEOGRAD 6|SF:189|S:UPLATA PO RAČUNU ZA EL. ENERGIJU|RO:97163220000111111111000
```

```json
{
  "K": "PR",
  "V": "01",
  "C": "1",
  "R": "845000000040484987",
  "N": "JP EPS BEOGRAD\r\nBALKANSKA 13",
  "I": "RSD3596,13",
  "P": "MRĐO MAČKATOVIĆ\r\nŽUPSKA 13\r\nBEOGRAD 6",

  "RO": "97163220000111111111000"
```

**F3** — пример из устаревшей редакции 2018 года (S5). Тот же текст, но
SF:189 и сумма 3596,13; в PDF переводы строк внутри N и P. Как
фикстура избыточен, совпадает с F2.

**Фрагменты из S6 (рекомендации)** — для юнит-тестов отдельных полей:

- R: `840-955845-10` → `840000000095584510`; `165-55-74` →
  `165000000000005574`; `310-1234567891211-86` → `310123456789121186`.
- N: `Čigra`, `Čigra doo Leskovac`.
- I верные: `RSD1025,`, `RSD1025,1`, `RSD1025,12`. Неверный: `RSD,01`.
- RO верные: `001234`, `9714123412`, `009714123`, `00009714-1342`.
- Модель 97 (S12): тело `567812F48K012` → `54567812F48K012`.

### 6.2. Некорректные строки из официальных документов (дословно)

**X1** [S8, generate → 620]. Завершающий `|`; теги вне порядка, что
допустимо; `RO:00dadss` — буквы после `00`, тоже допустимо:

```
K:PR|V:01|C:1|I:RSD3596,13|R:845000000040484987|P:1dsda89|S:UPLATA PO RAČUNU ZA EL. ENERGIJU|N:dsadsadsa|SF:189|RO:00dadss|
```

Ожидается: `{"code":620,"desc":"String cannot end with | character."}`.

**X2** [S8, validate → 608]. RO с неверным контролем по модели 97 и
завершающий `\r\n`:

```
K:PR|V:01|C:1|R:845000000040484987|N:JP EPS BEOGRAD\r\nBALKANSKA 13|I:RSD3596,13|P:MRĐO MAČKATOVIĆ\r\nŽUPSKA 13\r\nBEOGRAD 6|SF:189|S:UPLATA PO RAČUNU ZA EL. ENERGIJU|RO:9763220000111111111000\r\n
```

В документе: `608`, ошибки «The reference number is not according to
model97» и др. По нашей проверке нынешний валидатор на завершающий
`\r\n` отвечает раньше: `602 … Text cannot start or end with whitespaces.`

**X3** [S8, upload → 608]. Нет десятичной запятой: `I:RSD359613`,
ошибка «Invalid format of tag I. Entered: 'RSD359613'».

Все кейсы основаны на `K:PR|V:01|C:1|R:845000000040484987|N:JP EPS BEOGRAD|I:RSD3702,65|SF:289`

## 7. Сверка с open-source [вторично]

`medigeek/php-ips-qr-code` (S13, `src/IPSQRCodeParser.php`, ветка
master, последний push 2026-01-27) опирается на **старую** редакцию
2018 года и с действующей нормой расходится:

- `"PayeeApprovalReferenceCode" => '/^[0-9]{0,35}$/'` — RO только цифры
  и до 35. По норме 2020 года до 25, разрешены буквы и дефис.
- `"CurrencyAndAmount" => '/^RSD[0-9]{1,12},[0-9]{0,2}$/'` — совпадает с
  фактическим поведением валидатора.
- `"PayeeNameAndPlace" => '/^.{1,70}$/m'` — проверяет длину построчно, а
  не всего поля. Это расходится с нормой: 70 на все поле, включая
  переводы строк.
- `"OneTimePaymentCode" => '/^[0-9]{5}$/'`, RK отсутствует — тоже
  редакция 2018 года.

Вывод: брать регулярные выражения из сторонних библиотек без сверки
нельзя. Источник истины — S1/S4 плюс поведение валидатора НБС. На
GitHub есть и другие генераторы (JS/TS/Python/Java, поиск
`ips qr nbs`). Они не проверялись.

## 8. Открытые вопросы

1. Обязателен ли порядок тегов для банковских приложений. Норма и
   валидатор порядок не требуют, мы выдаем порядок таблицы.
   **НЕ ПРОВЕРЕНО**.
2. Входит ли quiet zone в размер 2,5–3,3 см. Минимальный размер модуля
   нормой не задан. **НЕ ПРОВЕРЕНО**.
3. Как разные банки обрабатывают `RSD0,00`. Норма разрешает, поведение
   приложений **НЕ ПРОВЕРЕНО**.
4. Проверяют ли банки mod 97 в RO при оплате по QR. По Одлуке о платним
   налозима должны отклонять. **НЕ ПРОВЕРЕНО** на практике.
5. Валидатор пропускает табуляцию и пробелы по краям значения N. Норма
   это явно не запрещает, рекомендация S6 п.3 — против. Генератор
   должен делать trim и схлопывать пробелы.
6. Каким переводом строки разделять строки в N/P, `\n` или `\r\n`.
   Валидатор принимает оба (`\r\n` занимает 2 символа из 70), в
   примерах НБС используется `\r\n`. Какой вариант лучше переваривают
   банковские приложения, **НЕ ПРОВЕРЕНО**.
