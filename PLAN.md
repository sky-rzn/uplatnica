# План разработки: веб-приложение для учёта счетов (Сербия)

Рабочее название — **Uplatnica**. Это статическое SPA без бэкенда. Все данные хранятся в браузере, синхронизации между устройствами нет, перенос делается через импорт и экспорт.

Результаты исследования (этап 0) — в `docs/research/`, сводка и открытые вопросы — в `docs/research/README.md`. Нормативная база: «Odluka o obliku, sadržini i načinu korišćenja obrazaca platnih naloga za izvršenje platnih transakcija u dinarima» (Sl. glasnik 55/2015 … 82/2024) и Prilog 1 к Odluci o instant-transferima (Sl. glasnik 125/2020) для IPS QR.

---

## 1. Цели и границы

**Что входит в MVP:**
- Разделы: «Квартира», «Налоги», «Налоги ИП (paušal)» и любые другие - пользователь создает сам.
- Счета двух видов: периодические (раз в 1–12 месяцев) и привязанные к конкретным датам.
- Сумма либо фиксированная, либо вводится при получении каждого нового счёта.
- Диаграмма в духе Ганта: одна строка на счёт, в строке блоки по периодам. Цвета: зелёный — оплачен, оранжевый — к оплате, красный — просрочен.
- Генерация уплатницы (Nalog za uplatu, образец 1) для печати и в PDF.
- Генерация IPS QR-кода по стандарту НБС, чтобы платить сканированием в мобильном банке.
- Импорт и экспорт всех данных.

**Что не входит (как минимум в первую версию):** сервер, аккаунты, облачная синхронизация, подключение к банкам.

## 2. Технологический стек

| Задача | Выбор | Почему |
|---|---|---|
| Сборка | Vite + TypeScript | Быстро, на выходе статика |
| UI | Preact или Svelte | Маленький бандл. React тоже подойдёт, если он привычнее |
| Хранилище | IndexedDB через Dexie.js | Индексы, транзакции, миграции схемы |

## 3. Модель данных

```ts
interface Profile {          // плательщик (может быть несколько: я, супруг, ИП)
  id: string;
  name: string;              // поле "Uplatilac"
  address: string;
  jmbg?: string;             // для шаблонов poziva na broj
  pib?: string;
}

interface Section {
  id: string;
  name: string;
  color: string;
  order: number;
  archived: boolean;
}

interface Payee {            // получатель; можно вынести в справочник
  name: string;              // "Primalac", для QR не длиннее 70 символов
  address?: string;
  account: string;           // 18 цифр в нормализованном виде
}

type DueRule =
  | { day: number | 'last'; monthOffset?: number }  // паушал: 15-е следующего месяца -> { day: 15, monthOffset: 1 }
  | { daysFromStart: number };                       // porez na imovinu: 45-й день квартала -> { daysFromStart: 44 }

type Schedule =
  | { kind: 'periodic'; everyMonths: 1|2|3|4|6|12; due: DueRule;
      start: string /* YYYY-MM */; end?: string;
      shiftToWorkday?: boolean }                     // перенос с выходного/праздника на следующий рабочий день
  | { kind: 'dates'; dates: string[] /* YYYY-MM-DD */ };

interface Bill {             // шаблон обязательства
  id: string;
  sectionId: string;
  profileId: string;
  title: string;             // "Infostan", "Porez na imovinu", "Paušal - doprinos PIO"
  payee: Payee;
  paymentCode: string;       // "Šifra plaćanja", 3 цифры (189, 253, 254...)
  purpose: string;           // "Svrha uplate", для QR не длиннее 35 символов
  model?: '97' | '11' | '';  // '' = без модели, в QR пишется "00"
  referenceTemplate?: string;// "{OPSTINA}{JMBG}{YY}" -> poziv na broj, KK для 97 дописывается сам
  amountMode: 'fixed' | 'variable';
  amount?: number;           // хранить в парах (целое число), не float
  currency: 'RSD';
  schedule: Schedule;
  graceDays?: number;        // через сколько дней после срока считать просрочкой
  notes?: string;
  archived: boolean;
}

interface Occurrence {       // хранится только если у периода есть данные пользователя
  billId: string;
  periodKey: string;         // "2026-11", "2026-Q4" или конкретная дата: идентификатор периода
  dueDate?: string;          // переопределение срока
  amount?: number;           // введённая сумма для variable
  reference?: string;        // переопределение poziva na broj (например, с бумажного счёта)
  paidAt?: string;
  paidAmount?: number;
  note?: string;
}
```

**Главное архитектурное решение:** периоды не создаются заранее на годы вперёд. Их вычисляет из `schedule` чистая функция `expand(bill, range) → VirtualOccurrence[]`. В базе лежат только **переопределения** (`Occurrence`) с ключом `(billId, periodKey)`. Что это даёт:
- изменение расписания не плодит мусорных записей;
- оплаченные периоды не теряются, потому что `periodKey` привязан к периоду, а не к номеру строки;
- база остаётся маленькой, а экспорт — компактным.

Если расписание изменили так, что у сохранённого `Occurrence` больше нет периода, такая запись всё равно показывается, но помечается как «вне расписания».

**Статус вычисляется, а не хранится:**

| Условие | Статус | Цвет |
|---|---|---|
| `paidAt` задан | paid | зелёный |
| не оплачен, `today > dueDate + graceDays` | overdue | красный |
| не оплачен, срок в пределах горизонта (N дней) или текущий период | due | оранжевый |
| `variable` и сумма ещё не введена | awaiting amount | оранжевый со штриховкой |
| срок в будущем | upcoming | серый или контурный |
| частичная оплата (`paidAmount < amount`) | partial | оранжевый с зелёной полосой (по желанию) |

Деньги хранятся только в целых парах (1 RSD = 100 para), чтобы избежать ошибок округления.

## 4. Движок расписаний (`src/core/schedule.ts`)

- `expand(bill, from, to)` для периодических счетов идёт от `start` с шагом `everyMonths`. Срок считается по `DueRule`: либо день месяца `min(day, последний день месяца)` со сдвигом `monthOffset` от начала периода (`'last'` — последний день), либо `daysFromStart` от первого дня периода. Срок может лежать за пределами периода (паушал за октябрь платится до 15 ноября).
- `shiftToWorkday`: если срок выпал на выходной или государственный праздник РС, он переносится на следующий рабочий день. Нужен календарь праздников (`holidays.ts`), включая православную Пасху и переносы. Примеры: паушал за январь 2026 — до 18.02.2026; porez na imovinu за IV квартал 2026 — до 16.11.2026.
- Для `dates` — фильтрация списка дат по диапазону.
- Формат `periodKey`: месячный `YYYY-MM`, квартальный `YYYY-Qn`, годовой `YYYY`, для дат — `YYYY-MM-DD`.
- Блок на диаграмме занимает интервал `[начало периода, конец периода)`. Для счетов на конкретную дату блок тянется от предыдущей даты (или от начала месяца) до даты срока, либо это фиксированный «маркер».
- Покрыть всё unit-тестами: 29–31 число, високосные годы, `end` раньше `start`, смена расписания при уже оплаченных периодах, переносы на рабочий день.

Это ядро приложения, поэтому его надо написать и протестировать первым, отдельно от UI.

## 5. Сербская платёжная специфика (`src/core/serbia/`)

Подробности и источники: `docs/research/uplatnica-account-reference.md`, `docs/research/real-bills.md`.

### 5.1 Счёт получателя
- Формат: `XXX-XXXXXXXXXXXXX-XX` (банк 3 цифры, номер 13, контрольные 2). Короткая запись `160-602-16` нормализуется дополнением середины нулями слева до 13 цифр: `160000000000060216`.
- Контрольные цифры считаются по ISO 7064 MOD 97-10: `98 − (первые 16 цифр × 100 mod 97)`, что эквивалентно `N18 mod 97 = 1`. Валидатор показывает ошибку прямо в форме.

### 5.2 Poziv na broj
- Лимит 23 знака без модели (включая 2 контрольные цифры); вместе с моделью — 25, как тег `RO` в QR.
- Модель 97: буквы A–Z → 10–35, справа дописать `00`, `KK = 98 − (N mod 97)`, две цифры с ведущим нулём, ставятся в начало. Дефисы запрещены; при вводе (mts печатает `50-300-011-4937106`) их надо убирать. Банк обязан отклонить платёж с неверным KK. Функции `computeModel97(body)` и `validateModel97(ref)`.
- Модель 11 (действующей нормой НБС не описана, используется Infostan): структура `P1K-P2K-P3`, части через дефис, у P1 и P2 своя контрольная цифра, у P3 нет. MOD 11 с весами 2, 3, 4, … справа налево без цикла; `11 − остаток`, результат 10 или 11 → 0. Проверено на реальном счёте Infostan.
- Пустая модель: контроля нет, в QR пишется `00`.
- Шаблоны с подстановками `{OPSTINA}` (3 цифры), `{JMBG}`, `{PIB}`, `{YYYY}`, `{YY}`, `{MM}`, `{Q}`. Для публичных доходов структура `97 KK OOO ID` (Pravilnik, Član 11/12); с 03.01.2025 «общий» poziv na broj запрещён. KK рассчитывается автоматически.

### 5.3 Šifra plaćanja
- Справочник — Prilog 3 к решению о платёжных поручениях, 52 основания: `docs/research/payment-codes.json`.
- Первая цифра — форма платежа: 1 наличные, 2 безналичные (онлайн, мобильный банк), 3 и 9 для физлиц не нужны. В QR допустимы только 1 и 2.
- Типичные: 189/289 — прочие платежи физлиц (только физлица), 253 — налоги и взносы (паушал, porez na imovinu), 221 — товары и услуги (finalna potrošnja), 222 — услуги javnih preduzeća.
- На бумажных счетах иногда печатают только 2 цифры основания (mts: «21»), а в QR тот же получатель ставит `189`, Infostan в QR ставит `122`. При импорте из QR код берётся как есть, без «исправлений».

Подробности: `docs/research/ips-qr.md`, эталоны: `tests/fixtures/ips-qr.json`.

Реальная строка со счёта Infostan:
```
K:PR|V:01|C:1|R:200220618010100048|N:JKP INFOSTAN TEHNOLOGIJE BEOGRAD|I:RSD1287,60|SF:122|S:OBJEDINJENA NAPLATA|RO:11804071936013-26093-1
```
- Теги для `K:PR`: обязательные `K V C R N I SF`, необязательные `P S RO RL` (`RO` и `RL` взаимоисключающие). Разделитель `|`, экранирования нет; `|` в начале или конце строки, пустые теги, пробелы по краям и BOM запрещены.
- Порядок тегов валидатор НБС не проверяет. Генерируем в каноническом порядке (`K V C R N I P SF S RO`), парсер принимает любой.
- `R` — ровно 18 цифр, контроль MOD 97 проверяется.
- `I` — `RSD` + сумма с запятой, без разделителя тысяч: `RSD1287,60`; допустимы `RSD1025,` и `RSD1025,1`; максимум `RSD999999999999,99`.
- `N`, `P` — до 70 символов на всё поле, до 3 строк через `\r\n` (перевод строки считается за 2 символа). `S` — до 35, одна строка. Значения обрезать и схлопывать пробелы.
- `SF` — 3 цифры, первая 1 или 2, основание из Prilog 3.
- `RO` — модель (2 цифры) + poziv na broj, всего до 25; для модели 97 без дефисов и с проверкой KK.
- **Кириллица запрещена** (валидатор отвергает), разрешена латиница с č ć ž š đ. Перед генерацией — транслитерация `sr-Cyrl → sr-Latn` (`translit.ts`). Infostan так и делает: бумага кириллицей, QR латиницей.
- Кодировка UTF-8. QR не выше версии 13, уровень коррекции M (до 331 байта) или L (до 425 байт), печатный размер 2,5–3,3 см. Длину в байтах проверяет наш генератор — валидатор НБС этого не делает.
- **Обязательно:** тесты на эталонных строках и ручная сверка через валидатор НБС (API `nbs.rs/QRcode/api/qr/v1/validate`, `/gen`) на этапе разработки. В рантайме приложение никуда не ходит.
- Использование: открыть QR на экране компьютера и отсканировать телефоном в мобильном банке, либо распечатать его на уплатнице.

### 5.5 Чтение IPS QR с бумажного счёта
Infostan, EPS, Telekom и многие другие уже печатают IPS QR на счетах. Поэтому стоит сделать:
- кнопку «Сканировать счёт» (камера или загрузка фото/PDF);
- парсер `parseIpsQr(string)`, который заполняет сумму, poziv na broj и назначение для текущего периода. Парсер терпимый: любой порядок тегов, нет `P`, `\n` или `\r\n` в многострочных полях, `SF` с первой цифрой 1;
- при создании нового счёта — заполнение всего шаблона из QR.

Для счетов с плавающей суммой это сильно экономит время, поэтому функцию стоит включить в MVP или в первую итерацию после него.

### 5.6 Пресеты
Данные и источники: `docs/research/taxes-and-utilities.md`. Пресеты хранить как JSON и подписывать датой актуальности.

- **Паушал** — 4 отдельных платежа (единого счёта нет), model 97, šifra 253, poziv na broj — годовой BOP из rešenja в ePorezi (меняется каждый январь, вводится целиком), срок — 15-е следующего месяца с переносом на рабочий день, суммы из rešenja (меняются ежегодно):
  - porez na prihode od samostalne delatnosti — `840-711122843-32`;
  - doprinos za PIO — `840-721313843-74`;
  - doprinos za zdravstveno osiguranje — `840-721325843-61`;
  - doprinos za nezaposlenost — `840-721331843-06`.
- **Porez na imovinu** (физлица) — `840-713121843-57`, model 97, šifra 253, поквартально, срок — 45-й день квартала (14.02, 15.05, 14.08, 14.11) с переносом. Poziv na broj брать из rešenja целиком; структура в Белграде (шифра городской общины или 501) не выяснена.
- **Infostan, EPS, mts** — счета получателей на сайтах не публикуются; шаблон заполняется из QR первого счёта (5.5). EPS: срок 28-е число; Infostan использует модель 11.
- Номер счёта публичного дохода общину не кодирует — она входит в poziv na broj.

## 6. Диаграмма (главный экран)

**Раскладка:**
- Слева закреплённая колонка с названиями счетов, сгруппированными по разделам. Разделы сворачиваются.
- Сверху шкала месяцев, отдельно выделены годы.
- Вертикальная линия «сегодня».
- Строка — счёт, блок — период. Ширина блока пропорциональна длине периода: квартальный блок занимает 3 месяца.
- Внутри блока при наличии места показывается сумма.

**Взаимодействие:**
- Масштаб: 6 месяцев / 1 год / 3 года. По умолчанию — «−3 месяца … +9 месяцев».
- Клик по блоку открывает панель периода: сумма (поле ввода для `variable`), срок, poziv na broj, кнопки «Оплачено» (с датой, по умолчанию сегодня), «Уплатница», «QR», «Отменить оплату», заметка.
- Фильтры: по разделу, по профилю, «только неоплаченные».
- В заголовке строки — итог по счёту за видимый год.
- В шапке: «К оплате сейчас: N счетов, X RSD» и «Просрочено: …».

**Реализация:** CSS Grid, где колонка — день или месяц, а блок задаётся через `grid-column: start / end`. Это проще, чем SVG, и даёт нормальную доступность. При сотнях строк хватит простой виртуализации по строкам.

**Мобильная версия:** горизонтальный скролл с закреплённой первой колонкой и дополнительный вид «Список»: ближайшие и просроченные счета, отсортированные по сроку. На телефоне список удобнее диаграммы для повседневных действий.

**Доступность:** кроме цвета, у каждого статуса есть иконка или узор (✓, !, штриховка), чтобы диаграмма читалась при дальтонизме. Контраст проверяется в светлой и тёмной теме.

## 7. Уплатница

- Форма «Nalog za uplatu» (образец 1) отрисовывается как SVG в миллиметрах, чтобы размер при печати совпадал с реальным бланком. Бланк 99 × 210 мм (треть A4).
- Поля и лимиты (Prilog 2): platilac, svrha uplate, primalac — по 3 строки × 35 знаков; šifra plaćanja 3; valuta; iznos 15; račun primaoca 18; model 2; poziv na broj 23; mesto i datum prijema; datum izvršenja; potpis platioca. Подписи на бланке по действующей норме: «platilac», «potpis platioca», «datum izvršenja» (не «uplatilac», «pečat i potpis», «datum valute»). IPS QR — в свободной зоне.
- Официальных координат полей в мм нет; в `docs/research/uplatnica-account-reference.md` — оценка ±3 мм по образцу. Перед режимом наложения замерить реальный бланк.
- Два режима печати:
  1. **Полный бланк** — рамки и подписи рисует приложение, печать на обычной бумаге.
  2. **Наложение** — печатаются только значения на готовый бланк из банка или почты. Нужна калибровка смещений X/Y в настройках и тестовая печать.
- Пакетная печать: выбрать несколько неоплаченных периодов и получить по 3 уплатницы на лист A4.
- Экспорт в PDF через pdf-lib со встроенным шрифтом, где есть č ć ž š đ и кириллица (например, Noto Sans или PT Sans). Шрифт хранится локально, без Google Fonts.

## 8. Импорт и экспорт

**Формат — JSON:**
```json
{ "app": "uplatnica", "schemaVersion": 1, "exportedAt": "...",
  "profiles": [...], "sections": [...], "bills": [...], "occurrences": [...], "settings": {...} }
```
- `schemaVersion` и цепочка миграций `migrate_v1_to_v2…`. Одни и те же миграции применяются и к IndexedDB, и к импортируемым файлам.
- Валидация через zod. Ошибки показываются с указанием пути к полю.
- Режимы импорта: **заменить всё** (с предварительным автоматическим бэкапом текущих данных) и **объединить** (по `id`, при конфликте побеждает более свежая запись, `updatedAt` есть на каждой сущности).
- Частичный экспорт: один раздел, чтобы поделиться набором шаблонов («налоги паушальца на 2027»).
- Опциональное шифрование файла паролем: WebCrypto, PBKDF2 и AES-GCM. JMBG — чувствительные данные.
- CSV-экспорт истории платежей — для Excel и бухгалтерии.
- **ICS-экспорт** сроков. Push-уведомлений без сервера нет, а календарь телефона закрывает напоминания бесплатно.

**Защита от потери данных:**
- `navigator.storage.persist()` при первом запуске, чтобы браузер не вычищал хранилище.
- Индикатор «последний бэкап N дней назад» и ненавязчивое напоминание.
- Опционально: File System Access API (Chromium) с автосохранением в выбранный файл, например в папке Dropbox или Syncthing. Получается синхронизация «для бедных» без сервера.

## 9. Прочее

- **i18n:** sr-Latn по умолчанию, sr-Cyrl, en, ru. Формат чисел `1.234,56`, даты `13.11.2026.` (с точкой в конце, как принято в Сербии). Ввод суммы принимает и `2.716,35`, и `2716.35` (так печатают некоторые получатели).
- **PWA:** офлайн-режим, установка на домашний экран, ярлык «Сканировать счёт».
- **Приватность:** никакой аналитики и внешних запросов, строгий CSP (`connect-src 'none'`), шрифты и библиотеки в бандле. Это стоит явно написать на главной странице, потому что это главное преимущество перед банковскими и облачными сервисами.
- **Темы:** светлая и тёмная.
- **Статистика (позже):** расходы по разделам и месяцам, сравнение с прошлым годом.

## 12. Риски

1. **Ошибка в IPS QR.** Банк не распознает код или, что хуже, примет неверные реквизиты. Защита: тесты на эталонах, сверка с валидатором НБС, обязательная валидация счёта и poziva na broj перед генерацией, транслитерация кириллицы, предпросмотр расшифровки рядом с кодом. Не проверено, как банковские приложения относятся к порядку тегов и к `RSD0,00` — проверить на 2–3 банках вручную.
2. **Потеря данных при очистке браузера.** Защита: `persist()`, напоминания о бэкапе, автосохранение в файл.
3. **Устаревшие налоговые реквизиты в пресетах.** Защита: дата актуальности у каждого пресета и предупреждение «проверьте в ePorezi».
4. **Печать не совпадает с бланком.** Защита: размеры в миллиметрах, печать без масштабирования (`@page { margin: 0 }`, подсказка «Масштаб 100 %»), калибровка.
5. **Юридическое.** Сайт только формирует платёжные данные и не проводит платежи. Достаточно дисклеймера.
